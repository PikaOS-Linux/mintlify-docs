These are the Wayland globals Zoolander advertises, with the highest version it offers. The protocol code lives in [Zooland](/developers/zooland/overview). Zoolander decides which globals to register and which clients may see them.

To see what a running session advertises, run `wayland-info` inside it.

## Privileged globals

Globals marked **Privileged** are hidden from clients that connect through `wp_security_context_manager_v1`. Flatpak and other sandboxes connect that way. Every other local client can bind them.

Privileged globals include data control, output management, virtual input, screen capture and session lock. Any process that can reach your Wayland socket can use them, so treat that socket as trusted session access.

### Workspace capture

`hyprland_workspace_image_capture_source_manager_v1` sources take an `ext_workspace_handle_v1`. Frames are the size of the workspace's output and are rendered offscreen, so a hidden workspace can be captured too.

- `windows_only` draws the workspace's windows and their popups on a transparent background.
- `everything` adds the backdrop, layer surfaces and pinned windows.

Frames follow that output's repaints, like output capture, and never include the cursor. A removed workspace gives transparent, empty frames.

### Cursor capture

Cursor sessions from `ext_image_copy_capture_manager_v1` follow the real cursor over output, window and workspace sources. A workspace source only shows the cursor while its output shows that workspace. The session reports when the cursor enters and leaves the source, and its position and hotspot in the buffer's pixels. The cursor image is copied at the source's scale, and a new copy waits for a new image, not for a repaint. A window or workspace moving under a still pointer updates the cursor position too.

## Window activation

Apps ask for focus through `xdg_activation_v1`. Zoolander moves focus only when the activation token was requested by the window that had keyboard focus when the token was made, or by one of its popups, and any input serial on the token is a recent press in that client. That is the case when you click a link in one app and another app opens it.

Every other activation only marks the window urgent. A chat app that activates itself on every new message does not take focus away while you type elsewhere. The window stays urgent until it gets keyboard focus. [`zoolanderctl clients`](/zoolander/ipc/zoolanderctl#clients) shows the urgent flag.

## Colour management

`wp_color_manager_v1` advertises:

| What | Values |
| --- | --- |
| Features | `icc_v2_v4`, `parametric`, `set_primaries`, `set_tf_power`, `set_luminances`, `set_mastering_display_primaries`, `extended_target_volume`, `windows_scrgb`, `windows_bt2100` |
| Named primaries | `srgb`, `pal_m`, `pal`, `ntsc`, `generic_film`, `bt2020`, `cie1931_xyz`, `dci_p3`, `display_p3`, `adobe_rgb` |
| Named transfer functions | `bt1886`, `gamma22`, `gamma28`, `st240`, `ext_linear`, `log_100`, `log_316`, `xvycc`, `st2084_pq`, `st428`, `hlg`, `compound_power_2_4` |
| Render intents | `perceptual` |

The deprecated `srgb` and `ext_srgb` transfer functions are not advertised, in favour of their replacements.

How Zoolander treats descriptions:

- Mastering display primaries and luminance go into the target volume, and from there into HDR metadata and the tone curve's peak. They never change the colour conversion itself, so a target volume larger than the primary volume is fine.
- Content with `st2084_pq`, `hlg` or `ext_linear` counts as HDR content for `hdr = "auto"` in [`zl.set_presentation`](/zoolander/configuring/variables#presentation).
- With `ext_linear`, 1.0 is the primary volume's maximum luminance. Values above it are kept, and its peak tone-maps like PQ.
- Windows scRGB keeps 1.0 at 80 cd/m², with a 10000 cd/m² target. The frog protocol's `scrgb_linear` uses the same target.
- `st240`, `log_100`, `log_316`, `xvycc` and `st428` decode with the exact inverse of the curves their standards define. `xvycc` keeps codes below 0 and above 1. For `st428`, code 1 is 52.37/48 of its 48 cd/m² white. Relative light from these curves maps to luminance through the same reference white as the other SDR curves.

The preferred description a surface gets is the one of the output it shows on. When a surface moves to another output, or an output's description changes because HDR switched or its EDID or display settings changed, clients hear it. Outputs send `image_description_changed` followed by `wl_output.done`. Surface feedback objects and frog surfaces get `preferred_changed2`, or `preferred_changed` below version 2.

A window that a [`force_game_hdr`](/zoolander/configuring/window-rules#force-hdr-for-a-game) rule matches, on an output that shows SDR, gets the description the output would have in HDR mode instead: PQ with BT.2020 primaries. Zoolander converts its PQ back to SDR. When the rule starts or stops matching, clients hear `preferred_changed`, so a Wine Vulkan subsurface hears it as well as the toplevel.

## Xwayland bypass

`zoolander_xwayland_bypass_v1` is a private Zoolander protocol. Its definition is `protocols/zoolander-xwayland-bypass-v1.xml` in [Zooland](/developers/zooland/overview). It lets an X11 client present a window's content through a `wl_surface` of its own, which can carry a `wp_color_manager_v1` description and HDR metadata where X11 cannot. Zoolander's Vulkan layer, `VK_LAYER_ZOOLANDER_wsi`, is its client. It follows gamescope's `gamescope_xwayland` protocol. Regular clients must not use it.

| Request or event | What it does |
| --- | --- |
| `get_window(id, x11_window)` | Follows a top-level window of Zoolander's Xwayland. The window object sends `mode` at once and on every change. |
| `mode` | `hdr` while a `force_game_hdr` rule matches the window, `x11` otherwise. An output in HDR mode alone keeps `x11`. |
| `set_content(id, surface, x, y)` | Makes `surface` a subsurface of the X11 window's own surface at `x`, `y`, above it. It follows the window's position, stacking, workspace, visibility and outputs, and is composited with its own image description. Input still goes to the X11 window wherever the surface's input region is empty. |
| `get_app(id, app_id, title)` | Answers once with the `mode` that the window rules alone would give a window with that app ID and title, before the app has windows. |

Only the process that owns the X11 window gets `hdr`, so no client can cover another's window. Zoolander checks the window's XRes client pid, else its `_NET_WM_PID`, against the Wayland client's pid. An unknown, unmanaged or override-redirect window stays `x11`. In `x11` mode, the subsurface from `set_content` is inert. `set_content` with a surface that has another role is a `bad_surface` error, and a second `set_content` on one window object is `content_exists`.

## Presentation feedback

`wp_presentation` feedback carries the `hw_clock` and `hw_completion` flags for flips the hardware timed, and `zero_copy` when the frame was scanned out directly from the client's buffer. While an output runs at a variable refresh rate, version 1 feedback reports a refresh of 0.

## Seat and pointer

On DRM, `wl_seat` advertises only the capabilities the connected input devices provide, and changes as devices come and go. A live virtual keyboard or pointer adds the keyboard or pointer capability. When the keyboard capability comes back after a replug or a VT switch, the focused window gets keyboard focus again. The headless and nested backends advertise every capability.

A pointer position change you did not make, such as a surface moving under a still pointer or a `wp_pointer_warp` warp, reaches version 11 pointers as `wl_pointer.warp` and older ones as motion. Pointers bound below version 8 get `axis_discrete` steps from high-resolution wheels.

Keyboard shortcut inhibitors hear `inactive` when their surface loses keyboard focus.

## Remote desktop seats

A remote desktop server can create a seat of its own through `ext_transient_seat_manager_v1`. Each transient seat is a separate `wl_seat` with pointer and keyboard capabilities:

- Its keyboard follows the main seat's focus, so a virtual keyboard on it types where local typing would.
- Its pointer keeps its own position. Virtual pointer input on that seat hit-tests and focuses on its own and does not move your cursor.
- Zoolander draws a software cursor for it at its pointer: the client's cursor surface, a cursor-shape theme image, or the default arrow. Captures that include cursors show it.
- A drag started on that seat shows its drag icon at that seat's pointer.

Destroying the seat cancels its drag and popup grab, erases its cursor and removes the global.

## Text input and input methods

- `show_input_panel` and `hide_input_panel` show and hide the input method's on-screen keyboard panel while that text input is active. Version 1 and 2 text inputs hear `input_panel_state`. Candidate popups and overlay panels stay visible.
- Version 2 text inputs hear `input_method_changed` when an input method arrives on or leaves the seat. When an input method activates, they are asked for 750 characters of surrounding text before the cursor and 250 after. That stays inside the 4000 bytes input method v2 allows, even at four UTF-8 bytes per character.
- Version 3 text inputs get the language an input method v1 reports. Return from an input method v1, in a field with the submit action, becomes the submit action.
- Preedit styling from an input method v1 reaches version 3 text inputs as `preedit_hint` events. Input method v2 has no styling, so its preedit text has no hints.

## Hardware

These need the DRM backend. The renderer and the device decide whether each one is registered.

| Interface | Version | Registered when |
| --- | --- | --- |
| `zwp_linux_dmabuf_v1` | 6 | The renderer imports dma-bufs (Vulkan with the dma-buf and DRM-modifier extensions). |
| `wl_drm` | 2 | Same, and the device has a render node. It names the render node, and buffers come through `create_prime_buffer`. |
| `wp_linux_drm_syncobj_manager_v1` | 1 | The device supports syncobj timelines. |
| `zwlr_gamma_control_manager_v1` | 1 | Privileged. An output has a gamma LUT. |
| `wp_drm_lease_device_v1` | 1 | Privileged. Always on DRM, even before a headset or other non-desktop connector is plugged in. |
| `zwlr_export_dmabuf_manager_v1` | 1 | Privileged. The Vulkan renderer draws outputs into exported scanout images, and frames are the scanout buffer itself. Not offered when frames are copied into dumb buffers. |

The software renderer imports no dma-bufs. On the nested and headless backends, and on DRM without Vulkan, Zoolander does not advertise `zwp_linux_dmabuf_v1` or `wl_drm`, so clients use `wl_shm` buffers.
