## Logs

Zoolander writes all its messages to standard error. It has no log file and no log level setting. Each line starts with a level and a scope:

```text
info(zoolander): DRM autodetect failed (...); falling back to headless
warning(zoolander_hotreload): config reload failed, keeping previous state: init.lua:12: ...
error(drm): modeset failed: ...
```

Lines from the Lua config start with `zoolander:` instead:

```text
zoolander: zl.set_blur: unknown field passes2
zoolander: zl.exec_command does nothing before compositor startup; use a startup handler or binding
zoolander: child 4242 exited with status 127 (exec may have failed)
```

Where the output goes depends on how you start Zoolander. A display manager sends it wherever it sends session output. To keep a copy, start Zoolander from a TTY and redirect it:

```bash
zoolander-session 2> ~/zoolander.log
```

## Check the running session

`zoolanderctl status` shows the renderer and whether the config loaded:

```bash
$ zoolanderctl status
OK reloads=1 fails=0 config_ok=true ssd=on renderer="vulkan on <GPU name> (<driver> <driver info>, /dev/dri/card1)"
```

| What you see | What it means |
| --- | --- |
| `renderer="vulkan on ..."` | DRM with the Vulkan renderer. |
| `renderer="software (dumb buffers on ...: Vulkan unavailable: ...)"` | DRM without Vulkan. See [Vulkan falls back to software](#vulkan-falls-back-to-software). |
| `renderer="software"` | The nested or headless backend. |
| `config_ok=false` | The last config load failed. Run `zoolanderctl reload` to see the error. |

See [zoolanderctl](/zoolander/ipc/zoolanderctl) for every command.

## Debug variables

Set these before you start Zoolander:

| Variable | Effect |
| --- | --- |
| `ZOOLAND_VK_VALIDATION=1` | Loads the Khronos Vulkan validation layer, if it is installed. |
| `ZOOLAND_VK_TIMING=1` | Logs GPU time and frame counters once a second. |
| `ZOOLAND_VK_ALLOW_UNMATCHED=1` | Lets the renderer use any Vulkan device, not only the one that drives the display. |

```bash
ZOOLAND_VK_TIMING=1 zoolander-session 2> ~/zoolander.log
```

[Environment variables](/zoolander/configuring/environment-variables#debug-variables) lists the other renderer debug variables.

## Black screen or no display

If DRM fails and you passed no backend flag, Zoolander falls back to the headless backend. It keeps running, but nothing appears on screen. The log shows one of:

```text
info(zoolander): DRM autodetect failed (<error>); falling back to headless
info(zoolander): DRM startup failed (<error>); falling back to headless
```

List the cards Zoolander can see and why it rejects any of them:

```bash
zoolander --drm-list
```

Then start on a specific card. An explicit `--drm` does not fall back, so the error stays visible:

```bash
zoolander-session --drm=/dev/dri/card1
```

Other causes:

| Cause | What to do |
| --- | --- |
| The driver has no atomic modesetting. The log says `DRM_CLIENT_CAP_ATOMIC unsupported by this driver; the backend has no legacy KMS path`. | Use a driver with atomic KMS support. |
| NVIDIA without kernel modesetting. | Load `nvidia-drm` with `modeset=1`. |
| `WAYLAND_DISPLAY` is set on a TTY, so Zoolander tries to run nested. | Unset it, or pass `--drm`. |

## Seat and device access

On DRM, Zoolander opens the GPU and input devices through libseat, which works with systemd-logind or seatd. The `zoolander` package depends on `seatd`. If libseat cannot open a seat, Zoolander opens the devices directly, which needs read and write access to `/dev/dri` and `/dev/input`.

If a device fails to open, the log shows:

```text
error(drm): opening "/dev/dri/card1" failed: <error>
```

Log in on a real TTY or through a display manager so you have an active seat. Do not start the DRM backend over SSH or from inside another desktop session.

Input devices come from the seat named by `XDG_SEAT`, or `seat0` when it is unset.

## Vulkan falls back to software

Zoolander renders with Vulkan on the GPU that drives the display. It never renders on another GPU unless you set `ZOOLAND_VK_ALLOW_UNMATCHED=1`. When Vulkan is not usable, it draws in software into dumb buffers and logs:

```text
info(drm): scanout path: dumb buffer (CPU/swrender) — Vulkan unavailable (<error>)
```

The session works but uses more CPU. To get Vulkan:

- Install a Vulkan 1.3 driver with dma-buf and DRM-modifier support for the display's GPU. On AMD and Intel, that is `mesa-vulkan-drivers`. On NVIDIA, use driver 515 or newer.
- Check that you have not set `VK_LOADER_DRIVERS_SELECT` to a driver for a different GPU. The packaged binary ignores `VK_DRIVER_FILES` and `VK_ICD_FILENAMES`; see [Variables that apps or Zoolander do not see](#variables-that-apps-or-zoolander-do-not-see).
- On a hybrid laptop, the display may be wired to the integrated GPU. Zoolander then renders there. Use `--drm-list` to see which card drives your panel.

Even with Vulkan, if the display plane and the driver share no scanout modifier, Zoolander copies frames into dumb buffers. That works but costs CPU time.

## Direct scanout does not engage

With direct scanout, the display shows a fullscreen game's buffer straight from the plane and Zoolander draws nothing for that frame. It is on by default (`direct_scanout` in [`zl.set_presentation`](/zoolander/configuring/variables)). To see whether it is active, and if not why, run:

```bash
zoolanderctl monitors | grep 'direct scanout'
```

The line shows `active`, or the first check that stopped the last frame. The reason updates every frame, so read it while the game runs in front.

| Reason | What stops direct scanout |
| --- | --- |
| `disabled` | `direct_scanout = false` in `zl.set_presentation`. |
| `no_window` | No window covers the whole output on its own. A border or title bar, a bar or notification on the `top` or `overlay` layer, a popup, the overview, a window drag, a move or resize, and the lock screen all count. Make the game fullscreen. |
| `animating` | An animation is running on the output. |
| `rotated` | The output has a transform other than `normal`. |
| `not_covering` | The window's content does not cover the output exactly. |
| `no_buffer` | The window has no buffer yet. |
| `color` | The buffer's colour encoding is not the output's, and the plane cannot convert it. See [HDR outputs](#hdr-outputs). |
| `transformed` | The client set a buffer transform. |
| `translucent` | The client made the surface less than fully opaque. |
| `subsurface` | The window has a visible subsurface. |
| `not_dmabuf` | The buffer is in shared memory, or Zoolander could not import it. |
| `size` | The buffer is not the size of the output's mode. Set the game's resolution to the output's. |
| `cropped` | The client crops its buffer with a viewport. |
| `format` | The plane cannot take the buffer's pixel format. Zoolander takes `XRGB8888`, `XBGR8888`, `XRGB2101010` and `XBGR2101010`, and their alpha variants when the client marks the buffer opaque. |
| `effects` | Window opacity, a fade, or inactive dimming applies to the window. |
| `capture` | A screen capture needs a frame that Zoolander draws. |
| `cursor` | A cursor overlaps the output and cannot stay on the hardware cursor plane. Tablet tool cursors and remote seat cursors count. Move the pointer to another output, or let the game hide it. |
| `popup` | An input method popup overlaps the output. |
| `carried_sources` | The previous frame was composited and its client buffers are still in use. Zoolander tries again on the next frame. |
| `rejected` | The kernel refused the plane setup. |

### HDR outputs

A game that renders PQ on an HDR output scans out like any other. A buffer tagged with the output's own colour encoding counts as a match.

An SDR game on an HDR output needs converting to PQ. Where the display plane has a colour pipeline, the display engine does that conversion and the game still scans out. `monitors` then shows `active (plane converts colour)`. The pipeline needs a kernel with plane colour pipelines (colorops) and:

- On AMD, a shaper 1D LUT and a 3D LUT on the primary plane.
- On NVIDIA, driver 615 or newer with its colour pipeline module parameter turned on.

`plane colour pipeline=false` means the output has no usable pipeline, and an SDR game on an HDR output composites with the reason `color`. Conversions the plane cannot reproduce, such as tone mapping, also composite.

The hardware cursor and a converting plane only mix on AMD RX 9000 series GPUs, whose display engine blends the cursor before the colour pipeline. There, a game with a visible cursor keeps direct scanout. On other GPUs, a cursor over a converted frame makes it composite with the reason `cursor`.

## A video player or game disconnects with "invalid luminance range"

Zoolander 0.1.27 and earlier disconnected Vulkan clients that pass HDR metadata with a `max_cll` or `max_fall` outside the mastering range, or `0` for unknown. The client failed with `invalid luminance range`. mpv's `gpu-next` hit this even with SDR video. Zoolander 0.1.28 accepts those values, so update the `zoolander` package.

## Xwayland

X11 apps need Xwayland. Zoolander looks for it at `/usr/local/libexec/zoolander/Xwayland`, then `/usr/bin/Xwayland`. The package depends on `xwayland`.

The X display listens from startup. Xwayland itself starts when the first X11 client connects, and exits 10 seconds after the last one leaves.

| Problem | Fix |
| --- | --- |
| Log shows `Xwayland startup failed: ...` | Install `xwayland`. Zoolander keeps running without X11 support. |
| X11 apps started from Zoolander have no `DISPLAY` | Check that your config does not call `zl.set_xwayland({ enabled = false })`. |
| X11 apps started by systemd or D-Bus have no `DISPLAY` | Export it from a `startup` handler: `dbus-update-activation-environment --systemd DISPLAY`. |

## Login environment is missing

The packaged `zoolander-session` wrapper loads `/etc/profile` with the POSIX `.` command before it starts Zoolander, so variables set there and in `/etc/profile.d/` reach the compositor and every client it starts. If a variable you expect is missing, set it in a file under `/etc/profile.d/`, or for clients only with [`zl.set_env`](/zoolander/configuring/environment-variables).

A source install's session file runs `zoolander` directly, without the wrapper, so it does not load `/etc/profile`.

## Variables that apps or Zoolander do not see

The `zoolander` package gives `/usr/bin/zoolander` the `cap_sys_nice` file capability, so its Vulkan queue can run at high priority and composite ahead of busy games. The log line `info(vk): graphics queue global priority:` shows the priority it got. `getcap /usr/bin/zoolander` shows the capability.

A program with a file capability runs in secure mode, which has side effects:

- glibc removes `LD_PRELOAD`, `LD_LIBRARY_PATH`, `TMPDIR`, `MALLOC_*` and a few similar variables from Zoolander's environment at startup. Apps that Zoolander starts never see them. Set them per app instead, for example in a game's launch options or a wrapper script.
- The Vulkan loader ignores `VK_DRIVER_FILES`, `VK_ICD_FILENAMES`, `VK_LAYER_PATH` and layers under your home directory for the compositor itself. Apps are not affected.
- You cannot attach `gdb` or `perf` to Zoolander as your own user. Use `sudo`.

To run without the capability, remove it with `sudo setcap -r /usr/bin/zoolander`. The queue then runs at default priority. A package upgrade puts the capability back.

## An app does not come to the front

An app that activates its own window, for example on a new chat message, only marks the window urgent. Focus moves only when the window that had keyboard focus asked for the activation, as when you click a link. `zoolanderctl clients` shows `urgent: true` for such a window until you focus it. See [Window activation](/zoolander/protocols#window-activation).

## Portals and screen sharing

`xdg-desktop-portal` uses `zoolander-portals.conf` only when its own environment has `XDG_CURRENT_DESKTOP=Zoolander`. Zoolander does not set that variable. Set it for clients and push it to the D-Bus environment:

```lua
zl.set_env("XDG_CURRENT_DESKTOP", "Zoolander")

zl.on("startup", function()
    zl.exec_command("dbus-update-activation-environment --systemd WAYLAND_DISPLAY DISPLAY XDG_CURRENT_DESKTOP")
end)
```

Then restart the portal service or log in again. See [Portals](/zoolander/installation#portals).

## Control socket

Zoolander does not start at all without `XDG_RUNTIME_DIR`, because it needs that directory for its Wayland socket.

| Message or symptom | Cause |
| --- | --- |
| `control socket disabled: path too long` | The socket path exceeds the Unix socket limit of 107 bytes. Use a shorter `XDG_RUNTIME_DIR`. |
| `zoolanderctl` fails from another terminal | That terminal's `WAYLAND_DISPLAY` points at a different compositor. Run `WAYLAND_DISPLAY=wayland-1 zoolanderctl status` with Zoolander's socket name. |
| `XDG_RUNTIME_DIR is unset` from `zoolanderctl` | Run it from a logged-in session, or set the variable. |

## The bell is silent

Zoolander plays the bell through PipeWire with `libzoolander_bell.so`, loaded on the first ring. Without a running PipeWire server or without that library, it logs a warning and carries on. Also check that your config does not call `zl.set_bell_sound("none")`.

## Clients connect to the wrong compositor

Zoolander removes `HYPRLAND_INSTANCE_SIGNATURE`, `HYPRLAND_CMD`, `NIRI_SOCKET`, `SWAYSOCK` and `I3SOCK` from the environment of clients it starts. Tools that look for those variables fail inside Zoolander rather than control another compositor. Use `zoolanderctl` instead. To restore one on purpose, set it with `zl.set_env`.

## Get back to a working config

If `init.lua` fails at startup, Zoolander loads its emergency config. You get <kbd>Super</kbd> + <kbd>Return</kbd> for `otter-term`, <kbd>Super</kbd> + <kbd>D</kbd> for `otter-launcher`, and <kbd>Super</kbd> + <kbd>Shift</kbd> + <kbd>Q</kbd> for `otter-logout`. See [First launch](/zoolander/installation#first-launch).

<Steps>
  <Step title="See the error">
    ```bash
    zoolanderctl reload
    ```

    The reply names the file and line, for example `ERR init.lua:14: ...`.
  </Step>
  <Step title="Fix and save">
    Edit the file and save it. Zoolander reloads on save. For a module in a subdirectory, run `zoolanderctl reload` again.
  </Step>
  <Step title="Confirm">
    ```bash
    zoolanderctl status
    ```

    `config_ok=true` means the config loaded.
  </Step>
</Steps>

If a reload fails while Zoolander is running, your previous config stays active until you restart.

To start with a known-good config without touching your own, pass another file:

```bash
zoolander-session --config=/path/to/known-good.lua
```

To start over from the starter config, move your config directory aside. On the next start, Zoolander copies the [starter config](/zoolander/installation#starter-config) into a new one:

```bash
mv ~/.config/zoolander ~/.config/zoolander.broken
```

Moving only `init.lua` aside is not enough. The starter's `init.lua` loads `monitors.lua`, `keybinds.lua`, `windows.lua` and `exec.lua`, and Zoolander keeps any of those that already exist.

The config directory watch stops if you delete or replace the directory itself. The log says `config directory watch removed; hot reload stopped, use zoolanderctl reload`. Reload by hand until you restart Zoolander.
