A plugin is a directory with a `plugin.toml` manifest and Lua source. The apps that load plugins are otr programs: the bar, launcher, dock, and taskbar each embed the `otter-lua` plugin host. The host owns layout, input routing, and rendering. Your script describes a frame with `sd.*` calls and reaches desktop services through `otter.*` modules.

For installation and Settings controls, see [Plugins](/desktop/plugins).

## How a host runs a plugin

The host gives each plugin its own sandboxed LuaJIT state. One event loop waits on every source a plugin created, such as timers, child programs, and file watches, then delivers each plugin's events in order.

A bar widget draws only when it calls `otter.host.redraw()`, when the bar resizes it, or after one of its events. An idle widget with no sources costs no wakeup and no Lua call.

You write an otr app only when you need a window or a daemon of your own. See [Creating an app](/developers/creating-an-app).

## Choose an extension

| You want                     | Contract                            | Starter                                  |
| ---------------------------- | ----------------------------------- | ---------------------------------------- |
| Bar widget                   | `measure`, `draw`, optional `event` | `opf new bar-widget my-chip`             |
| Launcher results             | `query`, `activate`, optional `row` | `opf new launcher-provider my-provider`  |
| Headless event-driven plugin | Entry script, optional exports      | `opf new plugin my-service`              |
| Whole Lua app                | `draw`, optional `event`            | `opf new app my-app`                     |
| Replace a supported app's UI | `frame`, optional `action`          | [UI scripts](/developers/lua/ui-scripts) |

The `app` starter runs under `otter-lua run`, which has a headless backend. For a Lua UI in a real Wayland window, start with the Lua UI template in [Creating an app](/developers/creating-an-app).

## Scaffold and check

Install the factory:

```bash
pikman install otter-plugin-factory
```

```bash
opf new bar-widget my-chip
cd my-chip
opf build
opf check
opf pack
opf check --build
```

| Command | What it does |
| --- | --- |
| `opf build` | Compiles every `.lua` file to check its syntax |
| `opf check` | Validates the manifest with the host's parser, loads the entry script, and calls its exports. It measures and draws a widget and queries a provider |
| `opf pack` | Copies the manifest, the Lua sources, and README and license files to `dist/plugins/my-chip/` |
| `opf check --build` | Packs first, then checks the packed copy too |

`opf check` loads the plugin in a sandboxed runtime that spawns nothing, reads no files, and starts no timers. `sd.*`, `otter.theme`, `otter.log`, and `otter.host` are real. `otter.fs`, `otter.timer`, and `otter.process` keep their capability checks but their calls do nothing. Other `otter.*` modules are inert. Use `opf check` for the contract, and test service integration in the real host.

## Manifest

This is the manifest of the `examples-counter` widget in `otter-examples/otr/plugins/`:

```toml plugin.toml
name = "examples-counter"
version = "0.1.0"
kind = "widget"
description = "The Otter Examples counter as a bar widget"
capabilities = []
```

| Key | Value | Default |
| --- | --- | --- |
| `name` | The plugin's name | Required |
| `version` | A version string | |
| `entry` | The entry script | `init.lua` |
| `kind` | `widget`, `plugin`, or `app` | `plugin` |
| `capabilities` | What the plugin asks to use, such as `"spawn"` or `"fs:~/.config/otter-shell"` | None |
| `provides` | The hosts the plugin is for | |
| `description` | Text that Settings shows | |

A launcher provider needs `kind = "plugin"` and `provides = ["launcher"]`. A dock tile needs `provides = ["dock"]`.

The parser reads `key = value` lines with strings, string arrays, and `#` comments. It rejects everything else, including an unknown key, so a misspelt key is an error.

Give the directory and the manifest the same name. Discovery, `plugin:<id>` layout names, and `plugins.conf` policy all use the directory name.

## A bar widget

A widget's entry script returns `measure`, `draw`, and an optional `event`. This is `examples-counter/init.lua`:

```lua init.lua
local host = require("otter.host")
local log = require("otter.log")
local theme = require("otter.theme")

local width = 132
local clicks = 0

-- Colours follow the theme: redraw when it changes.
theme.subscribe(function() host.redraw() end)

return {
  measure = function(max_w, max_h)
    return math.min(width, max_w), max_h
  end,
  draw = function(w, h)
    local t = theme.get()
    local size = math.min(14, h)
    sd.begin(w, h)
    sd.rect(0, 2, w, h - 4, theme.alpha(t.colors.accent, 0x28), t.layout.control_radius)
    sd.hit(1)
    local label = "Clicked " .. clicks .. (clicks == 1 and " time" or " times")
    sd.text(8, math.floor((h - size) / 2) - 1, label, size, t.colors.accent)
    sd.finish()
  end,
  event = function(kind, id)
    if kind == "click" and id == 1 then
      clicks = clicks + 1
      log.info("examples-counter: clicked", clicks)
      host.redraw()
    end
  end,
}
```

The bar calls `measure(max_w, max_h)` for the size the widget wants and `draw(w, h)` for the frame. `sd.hit(1)` tags the rectangle before it as hit area 1, and a click on it calls `event("click", 1)`. The widget needs no capabilities.

## A launcher provider

A provider returns `query` and `activate`. The launcher calls `query(text, max)` as you type and shows the entries it returns. This is the core of `examples-profiles/init.lua`:

```lua init.lua
local log = require("otter.log")
local process = require("otter.process")

local rows = {
  { title = "Otter Examples window", subtitle = "Surface Description card in an xdg toplevel", payload = "window" },
  { title = "Otter Examples overlay", subtitle = "the same card on a layer-shell surface", payload = "layer" },
}

return {
  query = function(text, max)
    local out = {}
    if not matches(text) then return out end
    for _, row in ipairs(rows) do
      if #out >= max then break end
      out[#out + 1] = row
    end
    return out
  end,
  activate = function(payload)
    log.info("examples-profiles: opening", payload)
    process.launch({ "otter-examples", payload })
  end,
}
```

`matches` is a local function in the same file that compares the query with the plugin's keywords. Each entry has a `title`, an optional `subtitle`, and a `payload` string. `activate(payload)` runs when you choose an entry.

`process.launch` needs the `spawn` capability, so the manifest declares it:

```toml plugin.toml
name = "examples-profiles"
version = "0.1.0"
kind = "plugin"
provides = ["launcher"]
description = "Launcher rows that open the Otter Examples card"
capabilities = ["spawn"]
```

## Install and discover

```text
my-chip/
  plugin.toml
  init.lua
  helpers.lua
```

Copy `dist/plugins/my-chip/` into `$XDG_DATA_HOME/otter-shell/plugins/`. While you develop, point `OTTER_PLUGIN_PATH` at `dist/plugins` instead.

Hosts search these roots in order, and the first matching directory name wins:

1. Each colon-separated `OTTER_PLUGIN_PATH` root.
2. `$XDG_DATA_HOME/otter-shell/plugins`, defaulting to `~/.local/share/otter-shell/plugins`.
3. `/usr/lib/otter-shell/plugins`.
4. `otter-shell/plugins` under each `$XDG_DATA_DIRS` entry, defaulting to `/usr/local/share` and `/usr/share`.

`OTTER_PLUGIN_SYSTEM_ROOTS` replaces the system roots for tests and development. An empty value excludes system plugins. The configuration directory holds policy and never plugin code.

Add a bar widget to `otter-bar.conf`:

```conf
layout_right = "plugin:my-chip,clock"
```

## Enable and grant capabilities

Policy lives in `$XDG_CONFIG_HOME/otter-shell/plugins.conf`, defaulting to `~/.config/otter-shell/plugins.conf`:

```conf
my-chip_enabled = true
my-chip_capabilities = ""
my-provider_enabled = true
my-provider_capabilities = spawn
```

A plugin gets a capability only when its manifest declares it and the policy allows it. With no `_capabilities` key, the policy allows every declared capability. An empty value allows none. `*` allows every declared capability and never adds an undeclared one.

A plugin is enabled unless its `_enabled` key says otherwise. The launcher makes five exceptions: `calc`, `emoji`, `clip`, `search`, and `snippet-provider` stay off until you enable them. The launcher has built-in results for the first four.

See [Bindings and capabilities](/developers/lua/bindings) before granting process launch or file access.

## Reload and failures

The host watches each plugin's Lua files and manifest. A change loads a candidate instance in a fresh runtime. If the widget was already drawn, the candidate must also measure and draw before it replaces the running instance. A candidate that fails leaves the old instance running, and the host records the error.

A runtime error, a heap cap failure, or a watchdog timeout unloads only the failing plugin. The host releases its timers, child programs, watches, and subscriptions, and every other plugin keeps running. Fix the files or click **Reload** to load it again.

The **Plugins** page in Settings shows each plugin's requested and granted capabilities, host status, heap use, reload and failure counts, and recent logs. [Runtime safety](/developers/lua/runtime) explains isolation and limits.
