Otter Shell v0.13.12 hosts extensions through LuaJIT. The Zig `.so` plugin ABI is unsupported. Each plugin has a `plugin.toml` manifest and Lua source. Native hosts own layout, input routing, and rendering; scripts describe frames through `sd.*`.

For installation and Settings controls, see [Plugins](/desktop/plugins).

## Choose an extension

| You want                     | Contract                            | Starter                                  |
| ---------------------------- | ----------------------------------- | ---------------------------------------- |
| Bar widget                   | `measure`, `draw`, optional `event` | `opf new bar-widget my-chip`             |
| Launcher results             | `query`, `activate`, optional `row` | `opf new launcher-provider my-provider`  |
| Headless event-driven plugin | Entry script, optional exports      | `opf new plugin my-service`              |
| Whole Lua app                | `draw`, optional `event`            | `opf new app my-app`                     |
| Replace a supported app's UI | `frame`, optional `action`          | [UI scripts](/developers/lua/ui-scripts) |

The `app` starter uses `otter-lua run`, whose current backend is headless. For a Lua UI in a real Wayland window, start with the native shell in [Creating an app](/developers/creating-an-app).

## Scaffold and check

Install the factory:

```bash
pikman install otter-plugin-factory
```

```bash
opf new bar-widget my-chip
cd my-chip
opf build
opf check
opf pack
opf check --build
```

- `build` syntax-checks every `.lua` file. It does not produce a native library or ship Lua bytecode.
- `check` validates the manifest, loads the entry script, and checks its exports. Widgets are measured and drawn; providers are queried.
- `pack` copies the manifest, Lua sources, and README/license files into `dist/plugins/my-chip/`.
- `check --build` packs first, then checks the packed copy too.

`opf check` does not spawn programs, access your files, or run timers. Its filesystem, timer, and process modules are inert substitutes; other service modules can be stubs. Use it to check the contract; test live service integration in the host.

## Manifest

```toml
name = "my-chip"
version = "0.1.0"
entry = "init.lua"
kind = "widget"
provides = ["bar"]
capabilities = []
description = "A small clickable status chip"
```

`entry` defaults to `init.lua`; `kind` defaults to `plugin`. Accepted kinds are `widget`, `plugin`, and `app`. `provides` lets hosts select compatible plugins before running their code. Launcher providers require `kind = "plugin"` and `provides = ["launcher"]`; dock extensions need `provides = ["dock"]`.

The parser accepts the manifest's supported string fields and string arrays, not arbitrary TOML. Unknown keys are errors. There is no `abi_version`, native `library`, or `provides_bar_widget` flag.

Use the same name for the directory and manifest when creating new plugins. Discovery, `plugin:<id>` layout names, and `plugins.conf` policy use the directory name.

## Install and discover

```text
my-chip/
  plugin.toml
  init.lua
  helpers.lua
```

Copy `dist/plugins/my-chip/` into `${XDG_DATA_HOME:-$HOME/.local/share}/otter-shell/plugins/`, or point `OTTER_PLUGIN_PATH` at `dist/plugins` for development.

Hosts search these roots in order; the first matching directory name wins:

1. Each colon-separated `OTTER_PLUGIN_PATH` root.
2. `$XDG_DATA_HOME/otter-shell/plugins`, defaulting to `~/.local/share/otter-shell/plugins`.
3. `/usr/lib/otter-shell/plugins`.
4. `otter-shell/plugins` under each `$XDG_DATA_DIRS` entry, defaulting to `/usr/local/share` and `/usr/share`.

`OTTER_PLUGIN_SYSTEM_ROOTS` replaces the system roots for tests and development. An empty value excludes system plugins. Configuration directories hold policy, not plugin code.

Add a bar widget to `otter-bar.conf`:

```conf
layout_right = plugin:my-chip, clock
```

## Enable and grant capabilities

Policy lives in `$XDG_CONFIG_HOME/otter-shell/plugins.conf`, defaulting to `~/.config/otter-shell/plugins.conf`:

```conf
my-chip_enabled = true
my-chip_capabilities = ""
my-provider_enabled = true
my-provider_capabilities = spawn
```

A plugin receives only capabilities requested in its manifest **and** permitted by policy. A missing `_capabilities` key permits every declared capability; an empty value permits none. `*` permits all declared capabilities, not undeclared ones.

Most plugins default to enabled. Launcher providers `calc`, `emoji`, `clip`, and `search` default to disabled because native launcher extensions already provide those results. `snippet-provider` is also opt-in. Custom providers are not universally disabled.

See [Bindings and capabilities](/developers/lua/bindings) before granting process launch or file access.

## Reload and failures

The host watches plugin Lua files and manifests. Reload builds a fresh candidate instance. A previously drawn widget must also measure and draw successfully before replacement. A failed candidate leaves the running instance intact and records the error.

A runtime error, memory-limit failure, or watchdog timeout unloads only the failing plugin. Its timers, child-process resources, watches, and subscriptions are released. Fixing its files or requesting **Reload** can load it again.

Settings' **Plugins** page shows requested and granted capabilities, host status, heap use, reload/failure counts, recent logs, and reload controls. [Runtime safety](/developers/lua/runtime) explains isolation and limits.
