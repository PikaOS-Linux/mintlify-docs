otr is a compiled systems language for desktop programs and services on Linux. Otter Shell's applications and libraries are written in it. The syntax is close to Zig and C, with Go's simplifications: no semicolons, no parentheses around conditions, and one loop keyword.

This section documents otr 0.2.6. The source is at [general-packages/otr](https://git.pika-os.com/general-packages/otr), and `docs/spec.md` in that repository is the full language specification.

```otr
import std

const Point = struct {
    x: f32
    y: f32
}

fn scale(ps: []mut Point, k: f32) void {
    for mut p in ps {
        p.x *= k
        p.y *= k
    }
}

pub fn main() void {
    var ps = [2]Point{ .{ x: 1, y: 2 }, .{ x: 3, y: 4 } }
    scale(&mut ps, 2)
    std.io.printf("{} {}\n", .{ ps[1].x, ps[1].y })
}
```

## What the language gives you

Safe code cannot use memory after it is freed, free it twice, race on it between threads, read it uninitialised, dereference null, or index out of bounds. Breaking any of these needs an `unsafe` block. The compiler checks this with a borrow checker that needs no lifetime annotations, because references cannot be stored in structs. Data that needs to point at other data uses [regions or pool handles](/otr/memory/regions-pools-and-cells) instead.

Cleanup is explicit. A value with a `deinit` method is a resource, and the compiler rejects any path that forgets to consume it. It never inserts the call for you, so every `defer x.deinit()` is in the source where you can read it.

Generics are Zig-style `comptime` functions that return types. A `where` clause can constrain a type parameter, and a body whose type parameters are all constrained by interfaces is type-checked once at its definition.

SIMD and data layout are language features. `simd for` either vectorises or fails to compile, `soa` stores a slice of structs as one column per field, and a release binary carries several CPU variants of its SIMD code and picks one at start-up.

C headers import directly with `import c "header.h" as h`. No binding generator or hand-written declarations are needed.

## The toolchain

One `otr` binary builds, runs, tests, formats, documents and serves the language server. Debug builds go through TPDE for fast compiles. Release builds go through LLVM. mold links both.

The installation is self-contained. It ships clang 23.1.3 with libclang, mold, TPDE, and the C libraries for every target (glibc and musl, for x86-64 and AArch64). Building and linking an otr program uses nothing from the host's toolchain, apart from the headers and libraries of other C libraries the program imports.

The compiler is written in otr and compiles itself. A compiler built by itself produces a byte-identical copy of itself, in debug and release builds.

## Limits to know about

otr targets Linux on x86-64 and AArch64 only. The packaged toolchain is built for x86-64 hosts.

The language has no operator overloading, exceptions, inheritance or macros. A panic prints a message and ends the process without running cleanup.

`otr.toml` accepts git dependencies but does not fetch them yet. Check the dependency out yourself and give its path.
